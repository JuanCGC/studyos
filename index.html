⇄ HTTP methods — idempotency

Idempotent (safe to retry)

  • GET — read, no side effects
  • PUT — full replace, same result
  • DELETE — removes, repeat = same state
  • HEAD — GET without body

Not idempotent

  • POST — create, calling twice duplicates
  • PATCH — partial update
Retry these carefully in tests
Idempotency is asked in every SDET interview. Explain it with an example in under 30 seconds.

◈ Test types

Functional

  • Happy path
  • Edge cases (null, empty, max)
  • CRUD flows
  • Field validation

Contract

  • JSON schema validation
  • Pact consumer-driven
  • Breaking change detection

Performance

  • Load (normal traffic)
  • Stress (beyond capacity)
  • Spike (sudden burst)
  • Soak (sustained)

Negative / security

  • Invalid inputs → correct errors
  • Missing auth → 401
  • Wrong permissions → 403
  • Injection → no 500
{ } RestAssured test anatomy
PostsTest.java — full example
@BeforeAll
static void setup() {
  RestAssured.baseURI = System.getenv().getOrDefault("BASE_URL", "https://jsonplaceholder.typicode.com");
  RestAssured.filters(new AllureRestAssured());
}

@Test
void getPost_validId_returnsCorrectSchema() {
  given()
    .pathParam("id", 1)
  .when()
    .get("/posts/{id}")
  .then()
    .statusCode(200)
    .body(matchesJsonSchemaInClasspath("schemas/post.json"))
    .body("id",     equalTo(1))
    .body("userId", notNullValue())
    .body("title",  not(emptyString()))
    .time(lessThan(1000L));
}

@ParameterizedTest
@ValueSource(ints = {-1, 0, 99999})
void getPost_invalidIds_return404(int id) {
  given().pathParam("id", id)
    .when().get("/posts/{id}")
    .then().statusCode(404);
}
{ } JSON Schema validation
schemas/post.json
{
  "type": "object",
  "required": ["id", "userId", "title", "body"],
  "properties": {
    "id":     { "type": "integer", "minimum": 1 },
    "userId": { "type": "integer" },
    "title":  { "type": "string", "minLength": 1 },
    "body":   { "type": "string" }
  },
  "additionalProperties": false
}
additionalProperties: false — catches when devs silently add or rename fields. Critical for microservice contracts.

Auth & security

OAuth, JWT, IDOR, and the full security checklist
🔧 Tools for this section

Postman

  • Pestaña "Authorization" para configurar tokens

  • Tests de seguridad sin código

jwt.io

  • Decodifica JWTs en el browser
  • Ver header, payload, signature
  • Gratis, sin login

ReqBin / Hoppscotch

  • reqbin.com — cliente HTTP online
  • hoppscotch.io — alternativa a Postman
  • Útil si no puedes instalar nada
◈ Security test checklist
  • ✓ No auth header → 401 (never 200 or 500)
  • ✓ Expired JWT → 401
  • ✓ Tampered JWT signature → 401
  • ✓ IDOR: user A accesses user B's resource → 403
  • ✓ SQL injection in params → no 500, no data leak
  • ✓ XSS payload in body → returned escaped
  • ✓ Rate limiting: 429 after N rapid requests
  • ✓ Password/SSN/credit card absent from all responses
  • ✓ HTTP redirects to HTTPS or refuses
  • ✓ Error messages contain no stack traces or DB info
{ } Auth test code
// Get token via client credentials
String token = given()
  .formParam("grant_type", "client_credentials")
  .formParam("client_id", CLIENT_ID)
  .formParam("client_secret", CLIENT_SECRET)
  .post("/oauth/token")
  .then().statusCode(200)
  .extract().path("access_token");

// Valid token → 200
given().header("Authorization", "Bearer " + token).get("/me").then().statusCode(200);

// Expired token → must be 401
given().header("Authorization", "Bearer " + EXPIRED_TOKEN).get("/me").then().statusCode(401);

// IDOR: user A token → user B resource → 403
given().header("Authorization", "Bearer " + USER_A_TOKEN)
  .get("/users/" + USER_B_ID).then().statusCode(403);

// Sensitive fields absent
given().get("/users/1").then()
  .body("password", nullValue()).body("ssn", nullValue());
🏋 Ejercicios — seguridad aplicada con Postman y jwt.io
Herramientas: Postman para enviar requests manuales, jwt.io para inspeccionar tokens, curl para pruebas rápidas.
Ex 1 — Inspecciona un JWT real en jwt.io
# 1. Ve a https://reqres.in/api/login (API pública con auth)
# 2. Haz POST con:  { "email": "eve.holt@reqres.in", "password": "cityslicka" }
# 3. Copia el token de la respuesta
# 4. Ve a jwt.io y pégalo
# 5. Responde:
#    - ¿Qué hay en el HEADER? (algoritmo de firma)
#    - ¿Qué hay en el PAYLOAD? (¿expira? ¿tiene claims de usuario?)
#    - ¿La firma se puede verificar sin el secret? ¿Por qué no?
# 6. Modifica 1 carácter del token y úsalo en Postman → ¿qué status recibes?
Ex 2 — Prueba de IDOR manual en Postman
# Usando reqres.in:
# 1. GET /api/users/1 sin token → anota el status
# 2. GET /api/users/2 sin token → anota el status
# 3. ¿Puedes acceder a datos de otros usuarios sin auth?
#    Si sí: eso es un IDOR (bug de seguridad real)
#    Si no: ¿qué status recibes? ¿401 o 403?
#
# La diferencia IDOR vs authz:
# - IDOR: accedes a resource de otro usuario con TU token válido → debe ser 403
# - No auth: sin token → debe ser 401
#
# En Postman, agrega este test al request:
pm.test("IDOR: user data not exposed", () => {
  pm.response.to.not.have.status(200); // si da 200 sin auth, es un bug
});
Ex 3 — SQL injection y XSS manual
# En Postman, envía estos payloads y observa el status y respuesta:
#
# SQL injection en query param:
# GET /api/users?id=1 OR 1=1--
# GET /api/users?id=1; DROP TABLE users;--
# ¿Responde 200, 400, 500? Si es 500 → bug de seguridad real
#
# XSS en body:
# POST /api/users  body: { "name": "<script>alert(1)</script>" }
# ¿El campo "name" en la respuesta viene igual o escapado?
# Si viene sin escapar → bug de seguridad
#
# Nota: JSONPlaceholder acepta cualquier body sin validar (es un mock)
# Para este ejercicio usa reqres.in o httpbin.org/post
Ex 4 — Rate limit: observa el 429
# En Postman, usa "Collection Runner" o el script de Pre-request:
# Envía el mismo request 20 veces seguidas y observa cuándo cambia el status.
#
# Con curl (bash loop):
for i in {1..20}; do
  echo "Request $i:"
  curl -s -o /dev/null -w "%{http_code}\n" https://jsonplaceholder.typicode.com/posts
done
#
# JSONPlaceholder no tiene rate limit real.
# Prueba con una API que sí lo tiene: api.github.com sin auth
# después de ~60 requests verás el 429 con header Retry-After
Ex 5 — Sensitive fields: construye tu propio checklist
# Para cualquier endpoint GET /users/{id} que uses en el trabajo:
# 1. Llama al endpoint y extrae TODOS los campos del response
# 2. Revisa cada campo y marca:
#    [ ] id           — OK (necesario)
#    [ ] name         — OK (necesario)
#    [ ] email        — ¿debería estar aquí? ¿quién lo ve?
#    [ ] password     — ❌ NUNCA en response
#    [ ] passwordHash — ❌ NUNCA en response
#    [ ] ssn          — ❌ NUNCA en response
#    [ ] creditCard   — ❌ NUNCA en response
#    [ ] internalId   — ¿debería exponerse?
#
# En RestAssured, agrega este test para los campos que NUNCA deben aparecer:
# .body("password",     nullValue())
# .body("passwordHash", nullValue())
# Este test vale más que 10 happy paths en un SDET interview.

◆ Pipeline stages — in order
  1. Build — compile, package, build Docker image
  2. Unit tests — fast, no network, target <2 min total
  3. Static analysis — SonarQube, linters, SAST tools
  4. Deploy to staging — ephemeral env spun up per PR
  5. API tests gate — your tests live here. Failure blocks merge.
  6. Performance gate — k6 smoke: p95 < 500ms, error rate < 1%
  7. Deploy to prod — only after all gates pass on main
  8. Smoke tests in prod — read-only sanity, no data mutation
{ } GitHub Actions — full eval gate
name: API Test Gate
on: [push, pull_request]

jobs:
  api-tests:
    runs-on: ubuntu-latest
    strategy:
      matrix: { java: [17, 21] }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '${{ matrix.java }}', distribution: 'temurin' }
      - uses: actions/cache@v4
        with: { path: ~/.m2, key: "maven-${{ hashFiles('**/pom.xml') }}" }
      - run: mvn test
      - uses: actions/upload-artifact@v4
        if: always()
        with: { name: "allure-java-${{ matrix.java }}", path: target/allure-results }
      - name: Notify Slack on failure
        if: failure()
        uses: slackapi/slack-github-action@v1
        with: { payload: '{"text":"Pipeline failed: ${{ github.ref }}"}' }
        env: { SLACK_WEBHOOK_URL: '${{ secrets.SLACK_WEBHOOK }}' }

Ex 4 — k6 smoke test localmente
# Instala k6 y corre tu primer performance gate:

# smoke.js
import http from 'k6/http';
import { check } from 'k6';
export const options = { vus: 5, duration: '10s',
  thresholds: { http_req_duration: ['p(95)<1000'], http_req_failed: ['rate<0.01'] }
};
export default function() {
  const r = http.get('https://jsonplaceholder.typicode.com/posts');
  check(r, { 'status 200': v => v.status === 200 });
}

# Corre: k6 run smoke.js
# Observa: vus, requests/s, p95, error rate
# Cambia el threshold a p(95)<10 → debería FALLAR
# Observa el exit code: echo $? → 1 (fallo)
# Esto es lo que bloquea un PR cuando performance falla

Many unit (fast/cheap) → some integration → few E2E (slow/expensive). SDETs balance confidence vs cost.
Test data in CI

AccountService.cls
public with sharing class AccountService {

  public class ServiceException extends Exception {}
  public class SyncResult {
    public String status;
    public String externalId;
  }

  // Update industry — tests FLS (WITH USER_MODE blocks without field access)
  public static void updateIndustry(Id accountId, String industry) {
    if (accountId == null) throw new ServiceException('Id cannot be null');
    Account acc = [SELECT Id, Industry FROM Account WHERE Id = :accountId WITH USER_MODE LIMIT 1];
    acc.Industry = industry;
    update as user acc;   // enforces FLS + sharing
  }

  // Bulk process — tests governor limits
  public static void processLargeDataSet(Integer count) {
    List<Account> accounts = [SELECT Id, Name FROM Account LIMIT :count WITH USER_MODE];
    List<Account> toUpdate = new List<Account>();
    for (Account a : accounts) {     // NO DML in loop — correct pattern
      a.Description = 'Processed at ' + DateTime.now();
      toUpdate.add(a);
    }
    if (!toUpdate.isEmpty()) update as user toUpdate;  // single DML
  }

  // External REST callout — requires HttpCalloutMock in tests
  public static SyncResult syncAccount(String externalId) {
    HttpRequest req = new HttpRequest();
    req.setEndpoint('callout:ExternalSystem/api/accounts/' + externalId);
    req.setMethod('GET');
    HttpResponse res = new Http().send(req);
    if (res.getStatusCode() != 200) throw new CalloutException('HTTP ' + res.getStatusCode());
    return (SyncResult) JSON.deserialize(res.getBody(), SyncResult.class);
  }
}

      - name: Run collection
        run: |
          newman run postman/collection.json \
            --environment staging.json \
            --reporters cli,htmlextra \
            --reporter-htmlextra-export reports/report.html \

import { Page, expect } from '@playwright/test';

export class FormsPage {
  constructor(private readonly page: Page) {}

  async goto()   { await this.page.goto('https://demoqa.com/automation-practice-form'); }

  async fillName(first: string, last: string) {
    await this.page.fill('#firstName', first);
    await this.page.fill('#lastName',  last);
  }

  async fillEmail(email: string) { await this.page.fill('#userEmail', email); }
  async fillPhone(phone: string) { await this.page.fill('#userNumber', phone); }

  async submit() {
    await this.page.click('#submit');
  }

  async expectSuccess() {
    await expect(this.page.locator('#example-modal-sizes-title-lg'))
      .toContainText('Thanks for submitting the form');
  }

  async expectValidationError() {
    await expect(this.page.locator('input:invalid, .field-error')).toBeVisible();
  }
}
